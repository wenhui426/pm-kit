# prd-html · PRD 驱动 HTML 交互原型

> pm-kit 内嵌的多页面 HTML 原型模块。
> 面向没有工程背景的产品经理，全程不接触代码、不接触工程概念。

## 一句话是什么

**PRD 是源，HTML 是影——你只写文字需求，能点的原型由运行中的 Agent 自动生成。**

## 核心思想

传统做法：需求 → PRD → 画原型 → 开发，三份东西各写各的，改一处、三处过期。
本方案：需求写成文字规格（MD），HTML 原型永远从规格生成，**改需求只改文字，页面由 AI 重新生成**，一致性由生成过程保证，不靠人工同步。

## 怎么用（用户视角只有三步）

```
① 说需求      "按这份 PRD 做 HTML 原型" / "这几个页面做成能点的"
              （发文档，或直接说页面名+功能）
② 给方向      页面多就告诉 Agent 哪些先做、谁跳谁（不说 Agent 也会推）
③ 验收反馈    Agent 生成完给你文件路径 → 浏览器打开点一点 → 说"这里不对" → 改
```

pm-kit 选择本模块后，会按页面规格、设计规范和逐页验收要求推进。

## 文件结构

```
prd-html/
├── procedure.md            # pm-kit 按需读取的执行规范
├── README.md                # 本文件，给人看的说明
├── assets/                  # 通用模板（所有类型共享一份）
│   ├── 导航地图模板.md       # 页面清单 + 跳转关系（骨架）
│   ├── 页面spec模板.md       # 每页规格示例（生成单元）
│   └── 公共规范-通用.md      # token 骨架（色板结构/字体/间距）
├── references/              # 单文件交付的执行细节
│   └── 单文件交付.md         # 单文件打包与验证清单
└── design-specs/            # 设计规范库（可自由增删）
    ├── index.md             # 规范清单 + 新增/修改/删除规则
    ├── 后台-通用.md          # 内置规范
    └── APP-通用.md           # 内置规范
```

## 设计规范怎么配置（重点）

项目的设计规范 = **通用骨架 + 类型规范 + 项目色板**，三部分拼装而成：

| 部分 | 在哪 | 怎么定 |
|------|------|--------|
| 通用骨架 | assets/公共规范-通用.md | token 名固定不用改；但**视觉签名和文案基调每项目必填** |
| 类型规范（布局+组件） | design-specs/ 下一个文件对应一个类型 | 现有后台、APP 两套；H5 待建，其他类型可继续加 |
| 项目色板 | 项目里 spec/_公共规范.md | 按项目替换 |

**配置一个新设计规范，只需要说一句**：

> "帮我建一套 XX后台 的设计规范"（或 APP/H5/其他）

然后任选一种来源给我：
- **发截图** → 我提取配色/组件/布局
- **发设计文档** → 我读取生成
- **口头描述** → 我按描述编写（"科技蓝主色，圆角卡片"）

配置完会存进 `design-specs/` 并登记进 index.md，以后开工会在清单里看到它，**点名即可选中，不用再配**。每次开工都会列清单确认选型，不会替你自动决定。

## 执行一次原型生成会产出什么

```
原型名\
├── spec\                    ← 过程文件（生成前的"施工图纸"，可评审可存档）
│   ├── _导航地图.md
│   ├── _公共规范.md
│   ├── 01-登录页.md
│   └── ...
├── src\                     ← 最终产物（HTML 页面集）
│   ├── assets\style.css     ← 公共样式（一致性靠它）
│   ├── assets\mock-data.js  ← 公共假数据
│   ├── index.html           ← 入口导航页
│   └── 01-login.html ...
├── 预览截图\                ← 验收截图（回看与交付预览，统一存放处）
├── <原型名>-完整交互原型.html ← 单文件交付版（可离线打开）
└── README.md                ← 交付说明
```

过程文件（spec/）不是负担：HTML 生成前打开它就能看出 Agent 对需求的理解对不对，发现偏差在"施工前"纠正，比生成完返工便宜。

## 质量保障（四道关卡）

```
spec 阶段：不许猜       需求没说明白 → 标记 [NEEDS CLARIFICATION] 停下来问，
                        不擅自假设（猜错一个字段，返工一个页面）
生成之前：过三道门禁      ① 样式用公共规范 token？ ② 跳转都在导航地图？ ③ 没引框架？
生成之后：逐条过验收清单   每页 8 条：能打开/布局对/跳转通/状态齐/风格统一/视觉签名/不落 AI 默认脸/文案基调
交付之前：整体验收一次     全部页面生成后你完整体验一遍，有整体性要求提出来，改到通过再打包单文件
```

## 截图放哪

- 固定目录 `<原型目录>/预览截图/`，一个原型只用这一处，不要散落在根目录或 `src/`。
- 命名与导航地图中的序号一致，如 `01-登录页.png`；同页不同状态可追加状态名。
- 截图工具的 `path` 直接指向该目录，不要先写根目录事后再整理。
- 源图片和用户参考图留在原位置读取，不复制进预览目录，也不要移动用户素材。
- 生成的 HTML 不依赖截图才能正常展示。

## 与 spec-kit 的关系

本 skill 借鉴了 spec-kit（规范驱动开发）的核心思想并裁剪掉工程部分：

| 借鉴 | 来源 |
|------|------|
| spec 是唯一事实源，产出物是派生产物 | spec-kit 核心思想 |
| 待澄清强制标记（不许猜） | spec-kit 模板机制 |
| 模板自查清单 / 生成前门禁 / WHAT 不写 HOW | spec-kit 模板约束机制 |
| 验收清单（验收场景先行） | spec-kit test-first 思想 |

| 裁剪（不适合个人原型场景） | 原因 |
|---|---|
| git 分支、特性编号 | 不需要版本管理仪式 |
| API 合约、数据模型、研究文档 | 超出原型范围 |
| specify/plan/tasks 命令链 | 太重 |
