# PRD 编写、审查与修订

## 1. 六步流程

### Step 0：开工确认

确认：

- 产品或功能名称
- PRD 类型：新产品、功能、改版、增量变更
- 读者：设计、研发、测试、运营、管理者
- 输入材料
- 交付格式
- 本次范围和不处理内容

信息已明确时直接进入下一步。

### Step 1：产品规划

从输入中形成产品定义，至少包含问题、用户、目标、范围和风险。缺失时使用 [product-planning.md](product-planning.md) 补齐。

### Step 2：生成 PRD

按以下结构组织；不适用的章节可以简化，但要说明原因。

```markdown
# [产品或功能名称] PRD

## 1. 文档信息
版本、状态、负责人、更新时间、变更摘要

## 2. 背景与问题
现状、证据、机会、为什么现在做

## 3. 目标与排除项
业务目标、用户目标、成功指标、明确不做

## 4. 用户与场景
角色、任务、使用环境、优先级

## 5. 产品方案概述
方案原则、能力范围、版本范围

## 6. 用户流程与信息架构
主流程、分支、页面关系、关键状态

## 7. 功能需求
按模块或用户任务拆分

## 8. 业务规则
触发条件、判断、处理、结果、失败处理

## 9. 页面与交互要求
页面目标、组件、操作、反馈、响应式要求

## 10. 数据、权限与埋点
字段、角色、权限、事件、指标口径

## 11. 异常与边界
空、错、加载、超时、无权限、重复操作、并发和恢复

## 12. 依赖、风险与发布
上下游、兼容、灰度、回滚、运营准备

## 13. 验收标准
可观察、可执行、可判定

## 14. 待确认事项
负责人、截止时间、影响范围
```

功能需求推荐格式：

```markdown
### FR-001 [功能名称]

- 用户目标：
- 前置条件：
- 触发方式：
- 主流程：
- 业务规则：
- 页面反馈：
- 异常处理：
- 权限要求：
- 数据与埋点：
- 验收标准：
```

### Step 3：质量审查

按五组检查：

1. 问题与范围：目标、边界、优先级、排除项
2. 用户与流程：角色、场景、主流程、分支、异常恢复
3. 需求与交互：规则完整性、状态反馈、文案、响应式
4. 数据与技术：字段、权限、埋点、依赖、兼容和性能
5. 交付与验证：验收标准、发布、灰度、回滚、未决事项

问题严重度和问题报告字段统一按 [评审、测试与验收](review-validation.md) 的定义：P0–P3 四级、七个字段。本文件不另立一套——两套分级会让同类问题在 PRD 审查报告和走查报告里编号不同，没法横向比较。

### Step 4：修订闭环

根据确认的问题修改文档，并维护问题状态：

- 已修复
- 接受风险
- 延后处理
- 等待确认

修订后复查受影响章节，尤其检查范围、流程、页面和验收标准是否同步。

### Step 5：收尾交付

交付：

- 最新 PRD
- 变更摘要
- 未决事项
- 审查结论
- 后续需要的交互、原型或验收任务

## 2. 验收标准写法

优先使用 Given / When / Then：

```text
Given 用户具备编辑权限且记录处于草稿状态
When 用户填写必填字段并点击“提交审核”
Then 系统保存数据、状态变为“审核中”，并展示提交成功反馈
```

同时覆盖失败条件、重复提交、权限不足和网络异常。

## 3. PRD 边界

- 不在 PRD 中虚构数据接口、法律结论或技术承诺。
- 不用页面截图替代业务规则。
- 不把设计建议写成已经确认的需求。
- 增量需求应说明对旧流程、数据、权限、埋点和验收的影响。
