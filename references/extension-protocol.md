# 场景、组件、模板与案例扩展协议

## 1. 目录边界

```text
catalog/
├── built-in/   技能自带资源
├── local/      使用者创建的资源
├── _schemas/   清单格式
└── index.json  扫描生成的总索引
```

技能升级可以更新 `built-in/`，不得覆盖 `local/`。

## 2. 四类资源

### scenario 场景

记录行业角色、典型任务、流程、业务状态、风险和反模式。

### component-library 组件库

记录组件映射、设计 Token、安装方式、组合规则、限制和验证方法。

### template 模板

记录 PRD、报告、原型、Brief、Journey、Pitch 等交付结构及必填字段。

### case 案例

记录脱敏后的输入摘要、工作流、决策、交付物和可复用经验。

## 3. 命名与版本

- 内置资源：`built-in:<slug>`
- 用户资源：`local:<slug>`
- slug 使用小写字母、数字和连字符。
- 版本使用 `major.minor.patch`。
- 状态使用 `draft`、`reviewed`、`active`、`deprecated`。
- 用户新建资源初始为 `draft`。

用户扩展通过 `extends` 继承已有资源，不直接覆盖内置资源。

`files` 里的路径**相对该资源的 `manifest.json` 所在目录**解析。它可以指向资源包之外（内置资源就指向 `references/`），但必须落在本 Skill 包内、且指向的文件真实存在——`catalog_manager.py validate` 会同时检查这两点。需要把一份资源连同它依赖的说明文件一起搬走时，先确认 `files` 里的每个路径在新位置仍然可解析。

新增流程能力与新增资源分开管理：流程能力登记在 `capabilities/registry.json`，并提供可读取的执行说明；场景、组件、模板和案例放在 `catalog/`。只增加团队 PRD 格式时，不需要新增技能入口或流程能力。

## 4. 发现与匹配

1. 扫描 `catalog/built-in/` 与 `catalog/local/` 中的 `manifest.json`；项目模板由 Agent 按第 5 节直接读取，不依赖目录索引。
2. 排除 `deprecated`。
3. 根据触发词、平台、任务模式和产出类型匹配。
4. 用户明确指定的资源优先。
5. 资源加载数量有上限，用来减少不同资源之间的规则冲突；上限见 `SKILL.md` 的「扩展资源匹配」，机器可校验版本在 [编排计划格式](../catalog/_schemas/workflow-plan.schema.json)。
6. 无匹配资源时使用通用工作流。

选择后在运行计划中列出资源 ID 和版本。

### 4.1 组合与继承的分工

一次任务会同时加载多份资源（上限见上一条），这就是**组合**——不同维度分别落在不同的资源位上：

| 维度举例 | 落在哪个资源位 |
| --- | --- |
| 行业做法（医疗、门店巡检） | 场景位 |
| 合规要求（等保、隐私） | 场景位 |
| 端与视觉规范（后台、APP） | 组件库位 |
| 团队交付结构 | 模板位 |

所以"医疗行业 + 移动端 + 合规 + 团队模板"这种四合一，**应当拆到四个资源位分别加载**，而不是塞进一条 `extends` 链。

`extends` 负责的是另一件事：**一份资源在另一份基础上精化**（一对一、同类，见第 5 节）。它拼不出"四合一"——那是设计意图，不是能力缺失。确实需要在同一类里叠多层时，先把共性提升为本包内置资源，或按第 7.1 节的规则合并。

**同类资源同时加载时怎么合并，见 7.1。**

## 5. 模板适配与覆盖

模板优先级从高到低：本轮用户明确指定的格式或模板路径、当前项目的 `.pm-kit/templates/`、`catalog/local/templates/`、`catalog/built-in/templates/`、通用交付标准。高优先级规则只覆盖同一字段或同一章节，不会使低优先级模板中的其他必要内容自动失效；如果两种要求无法并存，先请用户选择。

项目模板放在 `<project-root>/.pm-kit/templates/<slug>/`，包含 `manifest.json` 及其 `files` 指向的文件。Agent 先确认项目根目录，再按交付物类型读取候选模板。项目模板不进入全局索引，不会影响其他项目；用户只给出单个模板文件时，按明确路径读取，不要求创建资源包。团队长期使用且可复用的版本放进 `catalog/local/templates/`，通过目录索引发现。

`extends` 最多指定一个父资源，父资源须存在且类型相同，禁止循环继承。读取顺序为父资源说明文件、子资源说明文件、当前任务要求。`files` 中同名键由子资源覆盖，其余键继承；`required_fields` 等有顺序的清单由子资源给出完整有效列表，不做隐式拼接。继承只在 Agent 执行任务时按本协议解释；`catalog_manager.py validate` 负责清单结构与文件检查，不负责运行时合并。

模板中的保密或审批要求不能覆盖当前任务的明确授权边界；发现冲突时停止相关交付并询问。使用模板后在交付说明中标注模板路径或 ID、版本及本轮覆盖项。

## 6. 从项目沉淀资源

1. 识别可复用部分。
2. 选择资源类型。
3. 删除真实姓名、账号、密钥、客户数据和内部敏感信息。
4. 把项目名称、角色、指标和文案变量化。
5. 写明适用范围和不适用范围。
6. 展示归档内容并取得用户确认。
7. 使用 `scripts/catalog_manager.py scaffold` 创建骨架。
8. 填充内容并运行 `validate`。
9. 添加至少一个应使用和一个不应使用的测试场景。
10. 通过实际复用验证后把状态改为 `active`。

## 7. 资源冲突

- 相同 ID 不允许重复。
- `local` 与 `built-in` 使用不同命名空间。
- 多个资源同时匹配时，先按用户指定、平台一致、任务匹配和版本排序。
- 两个候选会产生不同结果时，进入用户决策门禁。

### 7.1 同时加载的同类资源怎么合并

两个场景（或两个模板）同时加载时，按下面的规则合并：

- **按具体程度排序，不按加载顺序**：本轮用户明确指定 ＞ 当前项目 `.pm-kit/` ＞ `catalog/local/` ＞ `catalog/built-in/`。
- **逐条合并，不是整份覆盖**：同一主题（同一业务对象的状态、同一角色的权限、同一流程节点）以高优先级资源的说法为准；**不冲突的条目全部保留**——整份覆盖会让叠加失去意义，组合的价值正在于各出一部分。
- **同层之间**（例如两个 `local` 场景）按适用范围更窄者优先：带行业或平台限定的优先于通用。判断不出来时进入决策门禁，不猜。
- **合并后仍然直接矛盾**（两条规则无法并存）→ 进入决策门禁让用户选；既不静默取一个，也不把两条都写进产物。已确认的选择按 [决策记录](decision-gates.md) 第 4 节写入跨轮记录。

## 8. 工具

```text
python -X utf8 "<pm-kit 根目录>/scripts/catalog_manager.py" discover
python -X utf8 "<pm-kit 根目录>/scripts/catalog_manager.py" validate
python -X utf8 "<pm-kit 根目录>/scripts/catalog_manager.py" rebuild-index
python -X utf8 "<pm-kit 根目录>/scripts/catalog_manager.py" scaffold scenario store-inspection --name "门店巡检"
```

`discover` 只列出当前能发现的资源；`validate` 才检查它们是否符合 schema 和协议，有问题时返回非零退出码。脚本默认以本 Skill 目录为根，`--root` 可指向别处（例如测试用的临时目录）。
