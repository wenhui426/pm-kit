# 跨轮协作、上下文隔离与产物依赖

在任务跨轮继续、同一项目有多个任务，或多个模块接力生成产物时读取本文件。读取协议不等于必须建立持久目录：一次性任务即使生成多份产物，只要没有后续接续、依赖追踪或分阶段确认需求，可在本轮保留来源、决定和一致性检查，交付后不建立项目记录。这里的“隔离”指项目文件与执行依据的逻辑隔离；同一聊天中的历史消息仍可能被运行环境提供。涉及敏感客户数据时，另用独立对话、独立目录和文件权限。

## 1. 身份与归属门禁

先确定 `project_id`，再确定 `task_id`，最后读取业务内容。项目名和任务名可修改，ID 保持稳定；同名项目使用不同 ID。用户没有指定 ID 时，以可识别名称加不重复后缀创建，不以项目名称直接覆盖已有目录。

按以下证据顺序判断归属：

1. 用户明确指定的项目、任务 ID 或目录。
2. 输入文件在产物索引中的所属项目、任务及版本。
3. 用户明确的关系表达，如“继续 A 的 PRD”“在同一项目新做 B”。
4. 项目名称、业务词或聊天位置仅作线索，不单独确定归属。

继续同一目标或修改同一产物时沿用原任务；同项目出现独立目标时新建任务；客户、产品或数据边界不同时新建项目。B 使用 A 的某份产物，应新建 B 并记录对 A 产物版本的引用。输入同时指向多个项目、关系不明且会改变结果时，只查看项目索引和产物索引的定位字段，暂停业务读取并请用户选择。同一对话可切换项目，不把前一项目的规则带入新项目。

## 2. 持久目录与读取边界

用户指定项目或模块产出目录时沿用用户路径。没有指定时使用：

```text
pm-kit-output/
├── projects.json                         仅存项目 ID、名称与目录定位信息
└── <project-id>/
    ├── project.json                      项目身份、共用规则版本与状态
    ├── business-rules.json               已确认或待确认的项目级规则
    ├── artifact-index.json               本项目产物版本和依赖索引
    └── tasks/<task-id>/
        ├── task.json                     本任务目标、计划、依据版本与状态
        ├── business-rules.json           仅对本任务生效的规则和假设
        ├── runs/<run-id>.json             每轮输入、执行、检查和断点
        └── artifacts/                    默认产物位置；可引用用户指定目录
```

用户指定项目集合根目录时，在该目录使用同一布局；只指定某个交付文件路径时，交付文件留在原处，项目记录放在已确认的项目目录。无法确定项目记录位置时先询问，不擅自建立另一套索引。

### 2.1 模块产物目录与项目记录的关系

专项模块（`make-prd`、`prd-html`、`html-prd`）各自要求用户指定自己的产物目录，这些目录**不搬到** `pm-kit-output/` 下。两类目录分工如下：

| 目录 | 属于谁 | 放什么 |
| --- | --- | --- |
| 模块产物目录（如 `PRD文档/`、`交互原型/`、`<输出目录>/`） | 模块 | 该模块的正式产物，以及它自己用于断点续做的工作记录（如 `过程记录/`） |
| `pm-kit-output/<project-id>/` | 本入口 | 只有跨轮才能知道的事实：项目与任务身份、已确认规则及版本、产物之间的依赖 |

在 `artifact-index.json` 里登记每条模块产物时，必须带上 `task_id` 和实际绝对路径，用它把两侧连起来。模块不必为了迁就记录而改自己的目录或文件名。模块自己的工作记录只服务该模块的断点续做，不能当作项目记录使用，也不能替代 `artifact-index.json`。

属于某个项目任务的模块产物，还要在自己的记录或交付说明里带上 `project_id` 与 `task_id`，一次性任务写 `null`。这样即使只读得到模块记录、读不到项目记录，也能找回它属于哪个项目。

项目身份未确认前只读取 `projects.json` 和必要的产物索引定位字段，不打开候选项目的业务规则或产物正文。确定后只读取本项目的项目级规则、产物索引及目标任务记录；其他任务正文须有用户指定或已登记的产物依赖才读取。跨项目比较仅打开用户指定的材料，不自动向另一项目写回。

`project.json` 至少记录 `project_id`、展示名称、`baseline_version`、项目状态和更新时间；有共用词汇表时记录路径。`task.json` 至少记录 `project_id`、`task_id`、本任务目标、采用的 `baseline_version`、任务状态、当前阶段、已确认任务决策、待决问题和最近一轮 ID。字段类型及取值见 [记录数据契约](record-contract.md)。各记录使用 `schema_version` 标明格式版本。文件缺失时只创建当前任务需要的记录，不为未发生的轮次预建空文件。

## 3. 业务规则记录

项目与任务两级 `business-rules.json` 使用相同字段。每条记录至少包含：

| 字段 | 用途 |
| --- | --- |
| `rule_id`、`revision` | 稳定编号与该规则的递增版本；旧版保留为历史记录 |
| `kind` | `requirement` 已要求的目标行为、`observation` 已观察实现、`assumption` 方案假设 |
| `statement`、`scope` | 规则内容与生效范围；范围明确到项目或任务、功能和角色 |
| `source` | 用户决定或材料的路径、位置、日期；观察结果注明页面与操作条件 |
| `status` | `unconfirmed`、`confirmed`、`superseded` |
| `confirmed_by`、`confirmed_at`、`supersedes` | 确认依据、时间和替代关系；未确认时留空 |

项目级 `baseline_version` 在已确认的项目规则更新时递增。任务级规则只对该任务生效，不改变项目基线；其他任务的产物不得直接依赖这类规则。需要供全项目使用时，先请用户确认适用范围，再追加到项目级记录并标明来源任务。`observation` 即使经过核实，也只说明当前实现，不自动变成目标 `requirement`。用户明确提出与已确认规则冲突的新要求时，先记录变更及影响；口径不明时询问，不静默改写旧规则。

## 4. 产物依赖与状态

`artifact-index.json` 为本项目每份产物记录：`artifact_id`、`task_id`、类型、路径、版本、状态、依赖的 `rule_id@revision`、依赖的上游 `artifact_id@version`、检查结果和最近更新时间。可计算时记录内容哈希；下轮使用前核对实际文件与索引，发现外部修改先重新判定版本。模块产物保留各自目录与命名要求；索引可指向用户指定的绝对路径，不强行搬动文件。

产物状态使用 `draft`、`reviewed`、`approved`、`superseded`；另外用 `freshness=current|needs_review` 标识依据是否仍有效。生成文件只得到 `draft`，完成质量检查可标 `reviewed`，用户或指定负责人确认后才标 `approved`。规则或上游产物更新时，查询直接依赖和下游依赖，全部标为 `needs_review`；修订并复查后，记录新的依赖版本，才能恢复 `current`。旧版本保留，不擅自覆盖。

交付说明必须给出当前产物状态和未验证项。`needs_review` 的文件不得标为当前已确认交付版；用户明确要求阶段性版本时可交付，但需标明旧依据、影响和待复查项。

## 5. 每轮固定交接循环

```text
确认项目与任务
→ 读取项目规则、任务规则、相关产物与上轮记录
→ 固定本轮 baseline_version 和输入产物版本
→ 选择并执行能力
→ 对照依据检查产物及变更影响
→ 写回规则、依赖、状态、轮次记录和下一轮断点
```

开轮时读取实际文件并核对记录；记录与文件矛盾时标出差异，不凭聊天记忆补写“已确认”。每个模块交接至少传递 `project_id`、`task_id`、采用的基线版本、输入产物版本、已确认规则、任务内假设、待决问题、输出路径、状态和检查结果。缺少必要输入时补做或暂停，不把草稿当作确认版。

轮次记录至少包含 `run_id`、本轮目标、采用的规则和输入产物版本、能力调用、用户决定、生成或修改的文件、检查结果、未决事项、当前阶段和下轮起点。等待用户确认时保存断点；收到答复后继续目标任务，不重做已确认阶段。任务 B 开始时建立独立轮次记录，不复用 A 的工作计划。

项目共用规则在任务执行期间变化时，比较任务固定的 `baseline_version` 与项目当前版本。版本不符先计算影响；仅在受影响内容复查后继续交付。无关变化记录为已检查，不重做无关产物。

写回项目级规则前再次读取当前 `baseline_version`。若其他任务已经更新基线，先对照双方变更并重新计算依赖，不用旧快照覆盖新记录。

三个内嵌模块沿用各自的阶段事实源：`make-prd` 的冻结产品规划、`prd-html` 采用的确认版 PRD/页面规格、`html-prd` 可观察的现有 HTML。项目规则变化后，先检查这些上游文件是否需要修订；下游模块不得绕过尚未更新的上游文件直接宣称已同步。现有 HTML 与已确认需求不一致时记录实现差异，不把观察结果直接提升为目标需求。

## 6. 最终检查与恢复

交付前用 `python -X utf8 "<pm-kit 根目录>/scripts/validate_records.py" <项目集合目录或项目目录>` 检查记录结构和已登记引用，再核对项目和任务 ID、规则确认状态、依赖版本、产物 `freshness`、待决问题、内容一致性及文件可用性。HTML 仍需浏览器交互检查；文档仍需回读或按格式要求渲染。未完成检查如实写在交付说明。项目/任务记录、源材料和实际文件互相冲突时先恢复可信状态，不擅自覆盖。

已有项目只有旧版 `context.json` 时，先读取并核对其来源、目标和产物，推断项目与任务归属；推断会改变共享范围时请用户确认。保留旧文件，确认后建立新记录并在轮次记录中引用旧文件路径，不自动删除或覆盖。

## 7. 例子

A 任务用 `make-prd` 确认 `REFUND-07@1`：“驳回后允许重新提交”，生成 PRD。下一轮用 `prd-html` 生成原型并登记依赖。B 任务分析同项目的现有 HTML，发现页面缺少该入口；`html-prd` 将其记为当前实现差异，不改写 A 的已确认规则。用户后来决定取消重新提交时，项目规则追加为 `REFUND-07@2`，依赖旧版规则的 PRD、原型和验收项标为 `needs_review`。B 的任务草稿不因此自动并入 A，也不进入另一个客户项目。
