# 冲突识别与用户决策门禁

## 1. 何时进入门禁

当不同路径会明显改变范围、交付形态、成本、技术路线或验收结果时，让用户选择。低风险、可逆、不会影响用户目标的实现细节直接处理。

## 2. 输出格式

```markdown
发现决策点：[冲突内容]

### 方案 A · [名称]（推荐）
- 交付结果：
- 限制或影响：

### 方案 B · [名称]
- 交付结果：
- 限制或影响：

推荐：方案 A，因为……

请确认本次走哪条路径。
```

最多给三个互斥选项。把你推荐的那条**排在第一位并标注“（推荐）”**，不要把它藏在后面；也不要为了凑数制造虚假的选择——两条真实路径胜过三条注水的。

## 3. 常见门禁

### 保真还原 / 产品改版

- 保真还原：保持原结构和视觉，只补明显交互。
- 产品改版：允许调整流程、结构和视觉。
- 双版本：分别交付还原版和改版版。

### 单文件 HTML / React 工程

- HTML：直接打开，适合评审和演示。
- React：适合开发接手，需要工程环境。
- 双交付：HTML 用于评审，React 用于开发。

### 局部修改 / 全局更新

- 局部：只改指定页面或文档段落。
- 全局：公共导航、组件、数据结构或规则变化时同步所有受影响产物。
- 先分析：只输出影响清单，暂不修改。

### 快速交付 / 正式交付

- 快速：先交主流程和草案，明确省略项。
- 标准：补齐必要状态和验证。
- 分阶段：先快速版本，再补正式版本。

### 组件库选择

- 遵循现有项目。
- 迁移到新组件库。
- 先输出迁移成本和差异。

### 来源冲突

- 采用当前用户确认。
- 采用指定正式文档版本。
- 保留两种方案，等待业务方确认。

## 4. 决策记录

代价较高、难以逆转、未来容易被误改的决定，除了写进产物，还要写进跨轮记录。**落点是明确的**：任务级存 `tasks/<task-id>/task.json` 的 `confirmed_decisions`；本轮留痕写 `runs/<run-id>.json` 的 `decisions`。两处元素形状相同，字段以 [记录数据契约](record-contract.md) 的 `decision` 为准：

```json
{
  "id": "decision-001",
  "topic": "prototype-technology",
  "choice": "single-file-html",
  "reason": "本轮用于评审和跨团队分发",
  "confirmed_by": "user",
  "confirmed_at": "2026-10-11T06:58:06+00:00",
  "affected_deliverables": ["prototype"]
}
```

`id`、`topic`、`choice`、`reason` 必填；`confirmed_by` 和 `confirmed_at` 在尚未确认时填 `null`，不能填猜测值。同一个决定在任务级只保留一条，改变时追加新 `id`，并在 `reason` 里写明它替代了哪一条。

后续要求与已确认决策冲突时，明确指出变化及影响，不静默覆盖。
