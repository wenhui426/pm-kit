# 工作流路由与调度

## 1. 这份文件负责什么

调度信息分三处，各管一件事。**改之前先确认该改哪一处**，不要互相抄：

| 你想知道的 | 看哪里 |
| --- | --- |
| 有哪些能力、每个能力读哪个说明文件 | [能力清单](../capabilities/registry.json) |
| 某类目标通常走哪条路径、交接条件是什么 | [编排参考](../workflows/recipes.md) |
| 调度时要遵守什么、多个交付物怎么排 | 本文件 |

本文件此前有一份按能力逐个罗列"输出可以包括……"的清单，与 `registry.json` 的 `produces` 重复，且两边已经出现不一致（同一场景一处含 `write-prd`、另一处只有 `build-prototype`），因此删除。需要某个能力的执行细节时，按清单里的 `instruction` 读对应文件。

先确定任务模式和执行深度，规则见 [task-modes.md](task-modes.md)。检测到会改变结果的路径冲突时，按 [decision-gates.md](decision-gates.md) 让用户选择。

## 2. 调度约束

- 同一次任务先确定目标交付物，再根据输入缺口组合能力；中途新增目标时更新执行计划。
- 只读分析不自动扩大为改版或文件修改。
- 用户要求生成时，完成必要的上游判断后直接生成，不强迫补齐完整项目流程。
- 多个交付物之间出现冲突时，优先使用最新确认的产品决策；没有确认依据时进入 [决策门禁](decision-gates.md)。
- 下一步建议最多给三个，按当前交付物的实际缺口排序。
- 复杂任务开始前展示“调用、跳过、决策点、交付物”四项；用户可以调整计划。
- 匹配扩展资源时遵守 [扩展协议](extension-protocol.md) 的加载上限，避免把整个知识库放入上下文。

## 3. 组合请求的步骤序列

用户一次要求多个交付物时，按依赖排序。

### PRD + 原型

```text
输入分析 → PRD 范围确认 → 交互设计 → HTML 原型 → 一致性检查
```

### 截图改版 + 说明文档

```text
截图分析 → 问题分级 → 改版目标 → 新交互方案 → HTML → 改版说明
```

### HTML 走查 + 修复

```text
读取 HTML 及依赖 → 功能与体验检查 → 问题清单 → 用户确认修复范围 → 修改副本 → 回归检查
```

### PRD 审查 + 修订

```text
结构与内容审查 → 分级问题 → 修订方案 → 更新 PRD → 复查关闭问题
```

## 4. 常见裁剪结果

这张表回答的是“已有材料能少走哪些阶段”，与 [编排参考](../workflows/recipes.md) 的路径表互补：那边说怎么走，这边说可以不走什么。

| 用户目标 | 本次能力组合 | 按已有材料可跳过 |
| --- | --- | --- |
| 只检查截图 | `analyze-input → review-validate` | 规划、文档和原型 |
| 会议纪要生成 PRD | `analyze-input → clarify-requirements? → plan-product? → write-prd` | 已确认范围时跳过规划 |
| 已有 PRD 生成原型 | `design-interaction? → build-prototype → review-validate` | 已有页面规格时跳过交互设计 |
| HTML 局部修改 | `analyze-input → build-prototype → review-validate` | 不受影响的文档和页面 |
| 完整产品项目 | 按最终产物及阶段交接选择能力 | 无固定全量路径 |
