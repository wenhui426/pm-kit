# 信息架构与交互设计

## 1. 输入

优先读取：

- 产品目标和范围
- 用户角色和关键任务
- PRD 或功能清单
- 现有页面、截图或 HTML
- 品牌和组件规范
- 端类型、屏幕范围和技术限制

输入不完整时，可以先完成结构草案；对业务规则有影响的空缺需要确认。

## 2. 信息架构

输出至少包含：

- 一级和二级导航
- 页面或视图清单
- 页面父子关系
- 每个页面的用户目标
- 全局入口、返回路径和跨模块跳转
- 权限或角色差异

页面命名使用用户可以理解的业务对象和动作，避免直接照搬数据库表名。

## 3. 用户流程

每条主流程写清：

```text
角色 → 触发条件 → 起点 → 操作步骤 → 判断分支 → 成功结果 → 失败恢复
```

至少覆盖：

- Happy path
- 用户取消
- 输入错误
- 权限不足
- 数据为空或已变化
- 网络或服务失败
- 重复提交
- 返回和恢复

复杂流程可以使用 Mermaid；同时提供文字说明，避免图表成为唯一信息源。

用户需要独立流程图、泳道图、矩阵泳道或可编辑 draw.io 文件时，将本阶段已明确的角色、活动、分支与异常出口交给 `flowchart-diagram`（按能力清单加载）。只要求图文件时不强制补写完整页面规格；图文件与 PRD、原型使用相同术语和规则版本。

## 4. 页面规格

每个页面使用以下结构：

```markdown
### P-01 页面名称

- 页面目标：
- 进入条件：
- 主要用户：
- 信息层级：
- 主要组件：
- 关键操作：
- 业务规则：
- 页面状态：
- 跳转关系：
- 权限差异：
- 响应式行为：
- 埋点建议：
- 验收要点：
```

## 5. 状态矩阵

| 状态 | 触发条件 | 页面表现 | 可执行操作 | 恢复方式 |
| --- | --- | --- | --- | --- |
| 初始 | 首次进入 | 默认内容 | 主操作 | 不适用 |
| 加载 | 请求未完成 | 骨架或局部进度 | 必要时允许取消 | 自动完成 |
| 空 | 无数据 | 解释原因和下一步 | 创建、导入或调整筛选 | 用户操作 |
| 错误 | 请求失败 | 明确错误和影响 | 重试、返回、联系支持 | 重试或人工 |
| 无权限 | 权限不足 | 说明访问限制 | 申请权限或返回 | 权限变更 |
| 成功 | 操作完成 | 明确结果 | 查看、继续或撤销 | 不适用 |

按实际产品补充离线、过期、冲突、审核中、部分成功等状态。

## 6. 交互规则

- 主操作在同一页面保持位置和命名稳定。
- 危险操作显示影响范围，并提供确认或撤销机制。
- 表单在接近输入位置显示错误；提交失败时保留用户输入。
- 异步操作提供进行中、完成和失败反馈。
- 筛选结果、分页位置和返回状态按任务需要保留。
- 弹层不能承载过长或多阶段的核心任务。
- 键盘操作、焦点顺序和可访问名称覆盖主要流程。

## 7. 响应式设计

明确：

- 主端与次端
- 页面在窄屏下的优先内容
- 导航变化
- 表格、图表和表单的收缩方式
- 鼠标、键盘和触屏操作差异
- 安全区、软键盘和固定操作区影响

## 8. 交付检查

- 页面清单覆盖全部主流程步骤。
- 每个操作都有结果反馈。
- 每个错误都有恢复路径。
- 权限差异反映到入口、内容和操作。
- PRD、页面规格和原型使用相同术语。
- 状态矩阵中的关键状态已经进入原型或验收清单。
