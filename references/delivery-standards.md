# 交付、上下文与变更标准

## 1. 默认交付目录

用户没有指定路径且任务需要跨轮保存时，按 [跨轮协议](cross-round-protocol.md) 第 2 节建立项目和任务目录——目录清单只在那一处维护，本文件不重抄。

只创建任务需要的文件和目录。用户指定路径时遵从用户路径；`make-prd`、`prd-html`、`html-prd` 的模块产物可以保留在各自确认的目录，由产物索引记录实际路径，不搬动既有文件。

## 2. 文件命名

- 使用简短、稳定、可识别的名称。
- 用户已有命名规范时遵循用户规范。
- 多版本文件添加版本号或日期，避免 `final-final-2`。
- 生成新版本时保留旧文件，除非用户明确要求覆盖。

## 3. 文档标准

文档应做到：

- 标题与范围明确
- 章节层级稳定
- 表格用于字段映射和比较，不堆长段文字
- 决策、建议和待确认项可以区分
- 数字、日期、版本和状态保持原始精度
- 重要结论能追溯到输入材料
- 验收标准可以执行和判断

用户未指定文档格式时输出 Markdown。用户明确要求 Word 时生成 `.docx` 并完成渲染检查。

## 4. HTML 标准

- 默认单文件、自包含、可直接打开。
- `<title>` 和页面内标题反映项目名称。
- 关键交互可操作。
- 没有明显控制台错误和失效资源。
- 窄屏、宽屏和主要状态经过检查。
- 使用模拟数据时有明确边界，不暴露敏感信息。

## 5. React 工程标准

- 包含运行说明和依赖说明。
- 环境变量使用示例文件，不写入密钥。
- 页面、组件和业务模块边界清晰。
- 模拟接口与真实接口边界明确。
- 类型检查、构建和关键路径检查完成。
- 未完成的接口、权限或测试范围写入交付说明。

## 6. 项目、任务与轮次记录

项目层使用 `project.json`、`business-rules.json` 和 `artifact-index.json`；任务层使用 `task.json`、任务级 `business-rules.json` 与 `runs/<run-id>.json`。字段格式见 [记录数据契约](record-contract.md)，读取边界、状态和跨轮写回步骤见 [跨轮协议](cross-round-protocol.md)。项目层只保存跨任务有效的信息；任务内计划、假设与未确认内容不自动进入其他任务。模块交接需携带项目与任务 ID、采用的规则版本、输入产物版本、输出路径及状态。

已有项目的 `context.json` 属于旧版项目记录。继续旧项目时先回读该文件及实际产物，确认归属后建立新记录，并在轮次记录中保存旧文件路径；不自动覆盖或删除旧文件。

**产物状态**使用（这是产物自己的生命周期；资源的 `draft/reviewed/active/deprecated` 是另一套词表，两者不要混用）：

- draft：已生成，尚未审查
- reviewed：已完成质量检查
- approved：用户或指定负责人已确认
- superseded：已被新版本替代

另外用 `current` 与 `needs_review` 记录产物依据是否仍有效。规则或上游产物变更后，依赖旧版本的产物及下游产物标记为 `needs_review`，不得作为当前已确认交付版。复查后才能恢复为 `current`。

不要把“已生成”写成“已确认”。

## 7. 变更管理

收到新需求或修改意见时：

1. 记录变更内容、来源、所属项目与任务，以及原规则版本。
2. 判断影响的目标、范围、流程、页面、数据、权限、埋点和验收。
3. 从 `artifact-index.json` 查询直接依赖与下游依赖，列出需要同步修改或复查的交付物。
4. 用户确认影响较大的方向后再修改。
5. 用户确认后追加规则或产物新版本，标记受影响旧产物为 `needs_review`，更新轮次记录。
6. 对受影响路径做回归检查，记录新的依赖版本与结果。

## 8. 交付说明模板

```markdown
## 已完成

- [交付物及用途]

## 文件

- [绝对路径]

## 已验证

- [打开、渲染、交互、构建或回归结果]

## 待确认或未验证

- [事项、影响和原因]

## 可继续推进

- [最多三个相关选项]
```
