## 1. 通用处理流程

对每项输入记录：

- 来源名称和路径
- 文件类型或信息形式
- 版本、日期或新旧关系
- 可直接确认的事实
- 可以推导但尚未确认的信息
- 对本次交付物的作用

读取文件时先保留原件。需要修改时生成新文件，除非用户明确要求覆盖。

## 2. 截图与图片

截图可提供视觉、结构和部分业务线索。按四层提取：

### 可观察事实

- 画布尺寸和端类型
- 页面区域、导航和内容层级
- 可见文字、按钮、字段和状态
- 颜色、字号、间距、边框、图标和图表
- 页面中已经出现的错误、空状态或提示

### 交互线索

- 可点击元素
- 页面跳转或弹层入口
- 表单依赖关系
- 筛选、排序、搜索和分页
- 选中、禁用、加载和反馈状态

### 产品推断

- 可能的用户目标
- 可能缺失的状态
- 可能需要的业务规则
- 可能存在的权限和数据依赖

推断必须使用“推测”“建议”或“待确认”标记。不要把截图中不可见的后端规则写成既定需求。

### 截图任务类型

| 用户目标 | 处理方式 |
| --- | --- |
| 还原 | 优先保持布局、视觉层级和文案，不擅自重设计 |
| 改版 | 先列现状问题，再说明改动与目标的对应关系 |
| 走查 | 按严重度提供证据、影响和修复建议 |
| 补全流程 | 区分截图已有内容和新增页面、状态、规则 |
| 提取规范 | 输出颜色、字体、间距、组件和复用建议 |

## 3. HTML 与前端代码

读取入口 HTML 以及它引用的本地 CSS、JavaScript、图片和数据文件。检查：

- DOM 结构和语义
- CSS 变量、布局、断点和状态样式
- JavaScript 事件、状态和数据来源
- 页面之间的路由或视图切换
- 外部 CDN 和网络依赖
- 表单、弹层、筛选、分页等交互是否有效
- 控制台错误、失效资源和无效链接

用户要求修改时，先确认交付形态：

- 保留现有技术结构并局部修改
- 基于现有页面生成新的单文件 HTML
- 在用户明确要求后转换为 React 工程

不要为了统一风格重写用户未要求修改的代码。

## 4. 文档

支持读取需求文档、PRD、会议纪要、用户研究、竞品报告、数据说明和验收记录。

提取时区分：

- 背景与问题
- 目标和指标
- 用户与场景
- 功能和业务规则
- 页面、流程和状态
- 数据与埋点
- 权限、依赖和限制
- 验收标准
- 明确排除项
- 冲突、歧义和缺失信息

保持原文中的数字、版本、日期和专有名词。重要结论可以附来源文件及章节，避免用户无法追溯。

## 5. 对话与文字

从对话中提取：

- 用户明确要求
- 已确认决策
- 用户否定过的方案
- 仍在讨论的候选方案
- 本轮新增限制

用户口头描述比较零散时，先整理成短版任务摘要供确认。已经明确的执行细节无需逐项复述。

## 6. 混合输入

混合输入先建立来源矩阵：

| 信息项 | 来源 | 状态 | 采用方式 |
| --- | --- | --- | --- |
| 业务目标 | PRD 第 2 节 | 已确认 | 直接使用 |
| 页面结构 | HTML | 当前实现 | 作为现状 |
| 视觉风格 | 截图 | 参考 | 只用于样式 |
| 新增规则 | 当前对话 | 已确认 | 覆盖旧文档 |

同一信息出现多个版本时，按 `SKILL.md` 的输入优先级判断；仍然判断不了时，把冲突具体列出请用户选择（选项见 [冲突识别与决策门禁](decision-gates.md) 的「来源冲突」）。

## 7. 输入冲突与缺口

缺口用统一标记 `[NEEDS CLARIFICATION: 具体问题]` 就地写在产物里。不要另起一份"待确认清单"就算标注完成——两份东西必然不同步，读产物的人只会看到其中一份。标记里写清缺什么、影响哪个决策、有没有临时候选。

以下缺口通常需要确认：

- 目标用户不同会改变产品流程。
- 成功指标缺失会影响方案取舍。
- 权限角色不清会改变页面和数据范围。
- 业务规则冲突会产生不同验收结果。
- 交付物将直接进入开发，但技术形态未确定。

以下缺口可以先给建议并标注：

- 次要文案
- 示例数据
- 图标选择
- 非关键动效
- 不影响主流程的视觉细节
