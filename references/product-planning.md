# 产品规划工作流

## 1. 适用范围

用于 `clarify-requirements` 需求澄清和 `plan-product` 产品规划。支持三种起点：

- 模糊想法：从问题和用户任务开始。
- 已有需求：提取现有结论并标出缺口。
- 改版项目：从现状问题、保留项和改版目标开始。

## 2. 规划顺序

### Step 1：问题与时机

明确：

- 当前发生了什么
- 谁受到影响
- 现有解决方式有什么成本
- 为什么现在处理
- 有哪些证据，哪些仍是假设

问题陈述建议采用：

```text
当［用户］在［场景］中尝试［任务］时，当前方案导致［可观察问题］，影响［用户结果或业务结果］。
```

### Step 2：用户与场景

至少说明：

- 主用户
- 次要用户或协作角色
- 触发场景
- 用户目标
- 当前替代方案
- 高频或高价值任务

不要用宽泛人群标签替代使用场景。

### Step 3：目标与指标

区分：

- 业务目标：收入、留存、成本、效率、风险等结果
- 用户目标：完成任务、减少等待、降低错误等结果
- 产品指标：衡量方案是否有效的指标
- 护栏指标：防止局部优化造成副作用

指标暂时没有基线时，标记“待补基线”，不要虚构数字。

### Step 4：方案与范围

先定义能力，再拆功能。范围至少包含：

- 本期必须完成
- 可以延后
- 明确不做
- 依赖其他团队或系统
- 需要验证的高风险假设

MVP 选择依据：用户价值、业务价值、风险降低和实现成本。

### Step 5：版本与风险

输出：

- MVP
- 后续版本候选
- 技术、数据、合规、运营和资源风险
- 每项风险的发现方式和缓解动作

## 3. 产品定义交付模板

```markdown
# 产品定义

## 1. 背景与问题
## 2. 用户与关键场景
## 3. 产品目标
## 4. 成功指标与护栏指标
## 5. 方案概述
## 6. MVP 范围
## 7. 排除项
## 8. 依赖与风险
## 9. 待确认决策
```

## 4. 规划质量检查

- 问题描述是否包含用户、场景和可观察影响。
- 目标是否可以指导范围选择。
- 功能是否能追溯到用户任务或业务目标。
- MVP 是否写清排除项。
- 指标是否有口径、观察周期和数据来源。
- 高风险假设是否有验证办法。
- 方案是否混入未经确认的业务规则。

## 5. 结构化澄清

当目标、用户、范围或业务规则仍有多个可能答案，并且差异会影响本次交付时，组织一轮有依赖顺序的澄清。先查文件、上下文和可用信息；问题只问用户需要判断或选择的内容。

整理待决事项时：

1. 把每项写成一个可回答的决定，例如“撤回后是否保留原审批记录”。
2. 标出决定之间的依赖。依赖尚未解决的问题先不提问。
3. 可以把互不依赖的问题放在同一轮，方便用户按编号回答；需要先后判断时分轮询问。
4. 提供可行选项、影响和建议。用户可以改写选项或补充第三种路径。
5. 当本次交付所需的目标、范围和规则已明确时停止澄清，不追求把所有未来情况问完。

如果用户已给出清晰目标和交付范围，直接进入对应节点。问题分析和原型探索能够解决的事实或体验问题，优先通过材料检查或可运行样例获取反馈，不用反复改写同一个问题。

## 6. 领域词汇与决策记录

当角色、业务对象、状态或同义词容易混淆，或项目会跨多人、多阶段继续时，按需在项目目录创建词汇表文件（默认 `domain-glossary.md`），并把路径写进 `project.json` 的 `glossary_path`。每个词条记录：

```markdown
**退款申请**：用户针对已支付订单提出的资金退回请求。申请通过后进入退款处理中。
_避免：退单、退货退款（除非项目明确表示同一概念）_
```

词条优先使用业务人员实际采用且已确认的名称。定义保持简短，记录容易混淆的近义词；不要把实现方案、页面文案草稿塞进词汇表。发现两个材料对同一词的定义不同，保留来源差异并请用户确认。

连续项目的共用词汇表放在项目目录，路径写进 `project.json` 的 `glossary_path`；任务专属词汇表放在任务目录，路径写进 `task.json` 的 `glossary_path`。单点任务只需在当前交付物中定义术语时，不额外创建文件。

决策分两层记录：

- 一般选择和用户确认：记录在 PRD 的待确认/已确认决策区；跨轮任务同步写入目标任务的轮次记录，项目共用规则按跨轮协议提升版本。
- 代价较高、难以逆转、未来容易被误改且来自真实取舍的决定：按 [冲突识别与决策门禁](decision-gates.md) 的格式，写进 `task.json` 的 `confirmed_decisions` 和本轮 `runs/<run-id>.json` 的 `decisions`。

不要为每个小选择创建决策记录。决定改变后追加新记录并标明被替代项，保留原有上下文。
