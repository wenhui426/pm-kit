# 原型生成规范

## 1. 原型用途选择

先区分探索型原型和交付型原型：

- **探索型原型**：方向或业务状态尚未确定，需要可运行样例收集反馈。
- **交付型原型**：方向已明确，需要形成评审演示或开发接手产物。

用户只说“做个原型”且没有提出未决问题时，默认按交付型原型处理。

### 探索型原型

当一个具体的 UI 选择或业务状态问题无法靠现有材料和简短讨论解决时，制作只回答该问题的原型。每次聚焦一个问题；需要比较多个方面时拆成多轮。

#### UI 方向探索

- 生成 2～3 个结构差异明显的方案，体现布局、信息层级或主要操作差异，不只调整颜色和文案。
- 有现有页面或产品风格时，在该上下文中比较；独立 HTML 中用明显的切换控件展示方案。
- 只接入演示所需的数据和交互，并标明模拟内容及探索问题。
- 让用户选定方案或拼合元素，记录选择及理由。

#### 业务状态探索

- 用一个可直接打开的单文件 HTML 展示状态、允许的操作和状态变化。
- 将状态逻辑与页面操作分开，使用纯函数或清晰的状态转换模块。
- 提供自由操作入口，以及覆盖主路径、关键边界和非法操作的引导场景。
- 每次操作后展示完整的相关业务状态，并用业务术语解释变化。
- 默认使用内存模拟数据，不连接真实服务或持久化数据。

开始前用一两句话写明“这个原型要回答什么”。演示达到可运行、可理解即可，不按正式交付原型的完整度建设。

收集反馈后，把用户确认的结论写入 PRD、交互规格或项目决策记录。若用户需要可评审的正式原型，再按交付型原型生成；探索演示不会自动视为最终交付物。

## 2. 交付形态选择

### 默认：单文件 HTML

用户提出“原型、Demo、页面还原、交互稿、可点击版本”且未指定技术栈时，生成单文件 HTML。

单文件 HTML 应具备：

- HTML、CSS 和 JavaScript 位于同一个文件
- 双击后可在现代浏览器打开
- 不依赖安装 Node.js 或执行构建命令
- 默认不依赖外部 CDN；确需远程资源时先说明
- 使用模拟数据演示主要流程
- 页面切换、弹层、表单、筛选等关键交互可操作

### React 工程

只有出现以下明确要求时进入 React 路径：

- 用户指定 React、Next.js、Vite 等技术栈
- 要求组件化工程或源码仓库
- 开发团队会在产物上继续开发
- 需要正式路由、复杂状态、真实 API 或权限框架
- 用户指定 Ant Design、shadcn/ui 等 React 组件库

页面数量多或交互复杂不能单独作为切换理由。用户指定单文件 HTML 时仍按单文件交付，并说明维护限制。

## 3. 单文件 HTML 生成流程

### Step 1：建立页面蓝图

从 PRD、截图或文字中整理：

- 页面或视图列表
- 主流程和跳转
- 布局区域
- 组件清单
- 数据与模拟状态
- 弹层和反馈
- 响应式要求

### Step 2：确定视觉依据

先判断用户要还原现有视觉，还是为新页面选择风格。还原任务中，用户指定的截图或现有 HTML 可直接作为视觉依据；只还原可观察部分，新增设计单独标注。新页面按以下顺序寻找依据：

1. 用户提供的设计规范
2. 用户明确指定作为目标风格的截图或现有 HTML
3. 当前产品已有风格
4. 与产品类型匹配的中性方案

有多个候选视觉规范且选择会明显改变结果时，列出候选请用户选择；不要从参考图的品牌或业务内容推断当前项目要求。用户授权自行决定、明确表示没有偏好，或没有可用规范且风格不影响本轮判断时，使用克制、中性、易读的设计，并说明采用依据。

### Step 3：实现结构和交互

至少实现用户明确要求的流程。根据任务选择：

- 视图切换或轻量路由
- 表单校验
- 搜索、筛选和排序
- 分页或列表加载
- 弹窗、抽屉、菜单和提示
- 成功、错误、空和加载状态
- 模拟新增、编辑、删除或状态变化

交互元素必须产生可见结果，禁止只绘制按钮而没有行为。

### Step 4：内容与数据

- 使用符合产品语境的示例数据。
- 保留用户提供的关键名称和数字。
- 推测的业务内容使用明显的示例标识。
- 不在原型中放置密钥、真实个人信息或未脱敏数据。

### Step 5：可访问性与适配

- 使用语义化元素。
- 输入项有标签。
- 图标按钮有可访问名称。
- 键盘可以完成主要操作。
- 焦点状态可见。
- 颜色不能成为唯一状态表达。
- 按要求支持桌面、平板或移动端。

### Step 6：验证

在浏览器中检查：

- 文件能正常打开，无资源加载失败。
- 主要页面和视图可以进入。
- 关键按钮、表单、弹层和状态切换有效。
- 刷新后的初始状态符合预期。
- 页面没有明显截断、遮挡和横向溢出。
- 窄屏和宽屏表现符合任务要求。
- 控制台没有影响使用的错误。

## 4. 截图还原规则

还原任务分为三种：

- 视觉还原：保持布局、字体、颜色、间距和层级。
- 交互补全：在视觉还原基础上补充可操作行为。
- 产品改版：保留可用结构，根据目标调整流程和页面。

开始前判断用户要哪一种。用户只说“照这个做”时，优先视觉还原并实现截图中明显可交互的元素；业务流程扩展列为建议。

## 5. React 工程规范

进入 React 路径后，明确或合理选择：

- 构建工具
- TypeScript 或 JavaScript
- 路由
- 组件库
- 状态管理
- 数据请求方式
- 测试范围

推荐目录：

```text
src/
├── app/
├── pages/
├── components/
├── features/
├── services/
├── mocks/
├── styles/
└── types/
```

交付前：

- 安装依赖
- 运行类型检查和构建
- 启动应用并检查关键路径
- 记录启动命令、环境变量和未接入接口

不要在用户未要求时创建部署、数据库或真实外部服务。

## 6. 原型与需求一致性

最终核对：

- 页面名称与 PRD 一致
- 主流程步骤一致
- 业务规则和按钮状态一致
- 权限差异一致
- 异常状态一致
- 指标或埋点所需触发点可识别
- 原型新增的设计决策已经记录
