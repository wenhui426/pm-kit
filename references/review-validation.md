# 评审、测试与验收

> 本文件只覆盖**专项检查**：需求审查、产品走查、无障碍、可用性测试、设计验收、发布验收——按用户目标选模式。
> 所有能力在交付前都要过的**通用门禁**在 `SKILL.md` 的「执行与质量检查」，不在这里。两者是两件事，都要过，不互相替代。

## 1. 选择检查模式

| 模式 | 检查对象 | 主要问题 |
| --- | --- | --- |
| 需求审查 | PRD、说明文档 | 能否准确开发和验收 |
| 产品走查 | 截图、原型、现有产品 | 流程和体验是否完整 |
| 无障碍检查 | 页面、HTML、原型 | 键盘、语义、对比度和辅助技术 |
| 可用性测试 | 原型或产品 | 用户能否完成关键任务 |
| 设计验收 | 设计参考与实现结果 | 实现是否符合设计和规则 |
| 发布验收 | 候选版本 | 主流程、数据、权限和回归是否通过 |

## 2. 问题报告格式

每个问题包含：

```markdown
### [编号] [问题标题]

- 严重度：P0 / P1 / P2 / P3
- 位置：页面、流程或章节
- 证据：截图、文件、操作步骤或原文
- 问题：可观察现象
- 影响：用户、业务、数据或交付风险
- 建议：具体修改方式
- 验收：如何判断已经修复
```

严重度建议：

- P0：阻断主任务，或存在严重数据、权限、合规风险
- P1：主要流程明显受损，用户容易失败，发布前应修复
- P2：体验或一致性问题，有替代路径
- P3：优化建议，不影响当前任务完成

不要只写“体验不好”“不够清晰”。指出具体位置、行为和后果。

## 3. 产品走查维度

- 目标与页面是否一致
- 信息层级和导航
- 主流程和分支
- 操作反馈
- 表单和输入
- 空、错、加载、权限和恢复
- 文案和术语一致性
- 响应式和多端差异
- 数据可理解性
- 高风险或不可逆操作

## 4. 无障碍检查

至少覆盖：

- 标题和地标结构
- 表单标签和错误关联
- 键盘可达性和焦点顺序
- 弹层焦点管理
- 图标和图片替代文本
- 文本与背景对比
- 状态不能只依赖颜色
- 动效减弱偏好
- 动态消息是否可被辅助技术感知

无法使用自动化工具时，明确哪些结论来自人工检查。

## 5. 可用性测试

测试方案包含：

- 测试目标
- 目标参与者
- 测试任务
- 成功条件
- 观察指标
- 主持提示
- 记录表
- 结论和改进优先级

任务描述给出目标，不直接告诉参与者操作步骤。

## 6. 设计与实现验收

比较：

- 页面结构
- 尺寸、间距和对齐
- 字体、颜色和图标
- 组件状态
- 文案与数据格式
- 交互和动画
- 响应式行为
- 异常和权限状态

区分三类差异：

- 实现缺陷
- 设计稿未说明
- 需求发生变更

## 7. 回归验证

修复后重新检查：

- 原问题是否关闭
- 修改是否影响相邻流程
- 状态和权限是否同步
- 文档、原型与实现是否仍一致
- 新增问题是否进入清单
